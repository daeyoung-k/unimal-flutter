# 마커 썸네일 파생 — 콜드 스타트 마커 표시 지연 근본 대책

- 작성일: 2026-07-29
- 상태: 클라이언트 조치 완료 / **서버 작업 미착수 (설계 제안)**
- 영향 레포: `unimal-server` (photo 모듈, board 모듈), `unimal-flutter` (마커 아이콘 생성)

## 배경

"앱 콜드 스타트에서 내 위치로 카메라가 이동한 **뒤에도** 마커가 한참 안 뜬다"는 체감을
계측으로 추적한 결과다. 이 문서는 측정값과 그로부터 확정된 원인, 클라이언트에서 이미
적용한 완화책, 그리고 **남은 유일한 근본 대책**을 기록한다.

측정 환경: iOS 시뮬레이터(iPhone 17), debug 모드, API는 `.env.local`(`localhost:8080`),
이미지는 실제 `cdn.unimal.co.kr`.

> **iOS 시뮬레이터는 항상 debug 모드다** (`flutter_tools/lib/src/ios/simulators.dart:541`
> — "The build mode for the simulator is always debug"). `--profile`/`--release` 를 쓸 수
> 없으므로 CPU 비용은 실기기보다 과장되고, 네트워크는 Mac wifi라 과소평가된다.

## 계측 결과

### 어디가 느린가

카메라 도착 이후 마커가 보이기까지의 구간 분해 (개선 전):

| 구간 | 값 | 비중 |
| --- | --- | --- |
| GPS 획득 | 136ms | — |
| 마커 조회 API | 207ms | 12% |
| **마커 아이콘 생성 루프** | **1456ms** | **87%** |
| `addOverlayAll` (네이티브 추가) | 3ms | 0.2% |

아이콘 생성 루프(`map_naver.dart` 의 `_loadMapMarkersInternal` 내 그룹 순회)는 그룹마다
CDN 다운로드 → 디코드 → PNG 인코드를 **직렬로 await** 하고, 마커는 루프가 끝난 뒤
`addOverlayAll` 로 한 번에 추가된다. 즉 **마지막 이미지가 도착할 때까지 마커가 하나도
보이지 않는다.**

### 원인은 파이프라인이 아니라 페이로드 크기

같은 코드 경로에서 이미지 크기만 다를 때:

| 이미지 | 앱 측정 | 참고: curl |
| --- | --- | --- |
| 30KB (`scaled_IMG_20260407_163130.jpg`) | **83ms** | 88ms |
| 큰 원본 | **1198~1326ms** | 3.3MB → 389ms(웜 연결) |

**30KB짜리는 이미 83ms다.** 직렬 루프, PNG 인코드, `overlayImageFromBytes` 전역 직렬
체인, `addOverlayAll` 은 전부 무죄다. 차이는 파일 크기 하나다.

연결 설정 비용도 배제됐다 (`curl` 실측):

```
콜드: dns=122ms tcp=137ms tls=158ms firstbyte=254ms
웜  : total=48ms
```

250ms는 1326ms를 설명하지 못한다. 남는 것은 바이트 전송이다.

### 실제 이미지 크기 (CDN 24장 전수 측정)

```
3,298,370 B  ← 최대 3.3MB
1,533,605
1,491,304
1,345,838
  ... 대부분 500KB ~ 1.5MB ...
   29,992 B  ← 최소 30KB (유일하게 작음)
총 약 22.5MB
```

**마커는 200px 원 안에 그리는데 최대 3.3MB를 받는다.** 필요량의 수백 배다.

### CloudFront에 리사이즈 기능이 없다

원본 3,298,370B 에 대해:

| 시도 | 응답 크기 |
| --- | --- |
| `?w=200` | 3,298,370 B |
| `?width=200` | 3,298,370 B |
| `?d=200x200` | 3,298,370 B |
| `?format=webp&width=200` | 3,298,370 B |
| `Accept: image/webp` 헤더 | 3,298,370 B (`content-type: image/jpeg`) |

→ **URL 파라미터로 해결하는 경로는 없다.** 파생 이미지를 서버가 만들어 저장해야 한다.

## 클라이언트 조치 (적용 완료)

| 조치 | 위치 | 효과 |
| --- | --- | --- |
| 디코드 축소 (`ResizeImage`, `fit` 정책) | `marker_image_factory.dart` `getImageStream` | 디코드 CPU/피크 메모리 절감 (약 10%) |
| 디스크 캐시 (`CachedNetworkImageProvider`) | 같은 함수 | **캐시 적중 시 1456ms → 416ms** |
| 업로드 압축 누락 경로 수정 | `share_card_sheet.dart` `_getImage` | 신규 업로드만 3.3MB → 800KB급 |

### 개선 결과

| | 값 | 신뢰도 |
| --- | --- | --- |
| 캐시 적중 (2회차 이후 콜드 스타트) | icon loop **416ms**, 사진 1장 **299ms** | **높음** — 네트워크를 타지 않음 |
| 신규 설치 (캐시 없음) | 694 ~ 2922ms (3회 측정) | **낮음** — 네트워크 조건이 지배 |

신규 설치 수치의 변동폭(4배)이 큰 이유는 측정 환경 노이즈다. 같은 기간
**localhost API 응답이 37~333ms로 9배 흔들렸다** (로컬 Spring 서버 워밍업 + Mac 부하 변동).
루프백 통신이 그렇게 변할 수는 없으므로, 신규 설치 구간의 절대값 비교는 이 환경에서
의미가 없다.

### 주의: 클라이언트에서 더 짜낼 것이 없다

- 남은 개선 여지(수십~수백 ms)가 이 측정 환경의 노이즈 폭(수천 ms)보다 작다.
  시뮬레이터 debug 측정으로는 더 이상 유의미한 판별이 불가능하다.
- 아이콘 루프 병렬화는 효과가 없다. 현재 데이터에서 두 번째 이미지가 83ms이므로
  병렬화해도 `max(1326, 83) ≈ 1326ms` — 절감 약 80ms. 마커 수가 크게 늘면 재검토.
- `CachedNetworkImageProvider` 의 `maxWidth`/`maxHeight`(축소본을 디스크에 저장)는
  `CacheManager` 를 `ImageCacheManager` 로 교체해야 한다. 아래 서버 파생이 들어오면
  불필요해지므로 손대지 않았다.

## 남은 문제

### ① 기존 이미지 22.5MB는 그대로다

업로드 압축은 **앞으로 올라올 사진에만** 적용된다. 이미 올라간 3.3MB 파일은 계속
3.3MB다. 신규 설치 사용자는 여전히 이 바이트를 받는다.

### ② 업로드 압축(1920px @ q85)으로도 마커용으로는 크다

`image_picker` 는 리사이즈한 파일에 `scaled_` 접두사를 붙인다. 즉 아래 둘은 **이미 압축
경로를 탄 파일**이다:

```
scaled_IMG_20260407_163130.jpg  →    29,992 B
scaled_20260630_231332.jpg      →   878,453 B  ← 압축했는데도 878KB
```

**1920px @ q85 결과물도 878KB가 나온다.** 200px 원 하나 그리려고 878KB를 받는 건 여전히
과하다. 업로드 압축은 4배 완화이고 근본책이 아니다.

### ③ 디코드 바닥 ~300ms 가 남는다

캐시 적중 상태에서도 큰 이미지 1장이 299ms다. **디스크에 3.3MB 원본이 저장돼** 매번
축소 디코드를 하기 때문이다(+ debug 모드 페널티). 200~400px 파일이면 이 비용도 거의
사라진다.

## 제안: 서버 썸네일 파생

세 문제를 한 번에 없애는 유일한 방법이다.

### 생성

`photo` 서비스가 업로드 처리 시 원본과 함께 마커용 파생을 만들어 S3에 저장한다.

- 목표 크기: **긴 변 400px** (종횡비 유지)
  - 400인 이유: 앱의 `createMarkerImage` 가 **중앙 정사각형을 크롭**해 200px 원에 그린다.
    400×400 에 fit 하면 4:3 가로 사진이 400×300 → 중앙 정사각 300px ≥ 200px 이라 어떤
    종횡비에서도 확대 흐림이 없다. 200으로 맞추면 200×150 → 150px < 200px 로 흐려진다.
    (같은 근거로 클라이언트 `kMarkerThumbDecodeSize = 400` 이 정해져 있다)
- 포맷: WebP 우선, 미지원 대비 JPEG 폴백
- 예상 크기: **20~40KB** — 측정된 30KB 파일이 83ms 였으므로 마커당 이 수준이 목표

### 응답

`MapPostInfo` 의 `file_info_list` 항목에 `thumbUrl` 을 추가한다.

```json
{
  "fileId": "N2q8WDpE",
  "fileUrl": "https://cdn.unimal.co.kr/images/...",
  "thumbUrl": "https://cdn.unimal.co.kr/thumbs/..."
}
```

`thumbUrl` 은 nullable 로 둔다. 백필 전 기존 이미지는 null 이고, 앱은 null 이면
`fileUrl` 로 폴백해 현재 동작을 유지한다.

### 백필

기존 24장(22.5MB)에 대해 일회성 배치로 파생을 생성한다. 이게 없으면 ①이 남는다.

### 앱 쪽 변경

- `MapPost` / `FileInfo` 모델에 `thumbUrl` 추가 (nullable)
- `map_naver.dart` 의 아이콘 생성이 `thumbUrl ?? fileUrl` 을 사용
- `ResizeImage`/디스크 캐시는 그대로 둔다 — 파생이 이미 작아도 해로울 것이 없고,
  `thumbUrl` 이 null 인 기간의 방어가 된다

### 기대 효과

| | 현재 | 파생 적용 후 (기대) |
| --- | --- | --- |
| 캐시 적중 | 416ms | 100ms 미만 |
| 신규 설치 | 694~2922ms | 수백 ms |
| 디코드 바닥 | 299ms | 거의 0 |

> 위 "기대" 수치는 측정값이 아니다. 근거는 "30KB 이미지가 같은 코드 경로에서 83ms"
> 라는 실측 하나다.
